## 현재 문제 (`src/content/pipeline.ts`)
1. `scan()`에서 세그먼트마다 `records.find(...)`, `request()`에서 IntersectionObserver 항목마다 `records` 전체를 돈다 → 세그먼트 수 N에 대해 O(N²). 1,000개 이상 페이지에서 느려짐
2. DOM이 조금만 바뀌어도(시계, 광고, 애니메이션 숫자) 300ms 디바운스 후 **문서 전체**를 다시 `findSegments` + 전체 해시 + 전체 `lookup` 전송

## 수정
1. **인덱스**: `records`와 함께 `Map<Element, RenderRecord[]>`(블록 → 레코드)와 `Map<string, RenderRecord[]>`(키 → 레코드)를 유지하고, 위의 선형 탐색을 모두 인덱스 조회로 바꾼다. `translated`·`cached`·`failed` 메시지 처리도 키 인덱스 사용
2. **증분 스캔**:
   - MutationObserver에서 바뀐 영역을 모은다: 추가된 노드의 가장 가까운 "스캔 루트"(세그먼트 블록이 될 수 있는 조상 또는 추가된 요소 자신), 텍스트가 바뀐 노드의 블록, 제거된 노드가 속했던 블록
   - 디바운스(300ms) 후 **모은 영역만** `findSegments(root)`로 다시 찾고, 그 영역 안의 기존 레코드만 교체·제거한다. 새 키만 `lookup` 보낸다 (이미 메모리에 있는 키는 바로 렌더)
   - 모은 영역이 너무 많거나(예: 50개 초과) `body` 직속 큰 교체(SPA 화면 전환처럼 본문 대부분이 바뀜)면 지금처럼 전체 스캔으로 대체
   - 같은 영역이 짧은 시간 계속 바뀌는 경우를 위해 **최소 간격**: 같은 블록은 1초에 한 번까지만 재스캔
   - `page` 메시지(페이지 키 목록 저장)는 전체 스캔 때와, 증분 스캔은 5초에 한 번까지만
3. 해시 계산은 이미 계산한 `markup → key`를 `Map`으로 캐시(최대 5,000개, 넘으면 비움)해 재스캔 때 재사용

## 테스트 (추가)
- 인덱스: 같은 키가 여러 블록에 있을 때 모두 렌더
- 증분: 문단 하나 추가 → 그 문단만 lookup (기존 키 재전송 없음)
- 증분: 한 문단 텍스트 변경 → 그 문단 레코드만 교체
- 같은 블록이 100ms마다 계속 바뀌어도 1초에 한 번만 스캔
- 대량 교체(본문 교체) → 전체 스캔으로 대체
- 성능: 세그먼트 2,000개 합성 문서에서 첫 스캔 + 문단 1개 추가 후 증분 스캔 시간 측정 (증분이 전체보다 10배 이상 빠른지 단언하지는 말고 측정값만 출력), `findSegments` 호출 횟수로 증분 범위 단언
